# Publisher approval and Cloud roles (experimental)

A namespace request starts `pending`. An authenticated Cloud admin may call `POST /api/v1/admin/publishers/{id}/approve`; an admin who is a member of that publisher is refused. Approval changes the status and writes an audit event in the same transaction. It does not register a public key, sign a registry delegation, or permit package publication. A separate signing-key lifecycle is implemented, but enrollment and approval remain disabled until session-bound step-up is available; no registry delegation or publication is performed.

Cloud account roles are separate from Better Auth identity roles. The explicit database operator commands are `cloud-api grant-role USER_ID admin OPERATOR` and `cloud-api revoke-role USER_ID admin OPERATOR`; `moderator` is also a supported role but has no moderation capability yet. Run migrations first. A successful change writes an audit event, a repeated no-op does not, and the command refuses to revoke the final admin. The operator label is supplied on the command line and is **not authenticated evidence of who ran it**: restrict database and shell access, and correlate it with independently authenticated operator logs. No HTTP role-management endpoint exists. This bootstrap mechanism is not a substitute for production access-control review.

The last-admin guard applies only to the explicit role command. Deleting an auth account cascades its Cloud role and can still remove the last admin; publisher-owner deletion and audit retention are not yet resolved. Approval is serialized with role revocation and membership changes, but it is not a replacement for independent security review or a complete approval UI.
