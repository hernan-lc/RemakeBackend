# Cloud API v3: catalog, remote control and integrations

Status: implemented on the backend and covered by PostgreSQL integration tests
(`cargo test -p cloud-api -- --ignored`). This document describes what exists
and what does not. It does not claim production readiness: see the
[feature matrix](FEATURE-MATRIX.md) and [implementation status](IMPLEMENTATION-STATUS.md).

v2 remains the compatibility contract. v3 is additive: v2 routes, collections,
cursors and semantics are unchanged. `GET /api/v2/capabilities` gains three
objects (`presentationCatalog`, `remoteControl`, `integrations`); v2 clients ignore
them.

## Envelope and correlation

Every `/api/v3` response carries an `x-request-id` header generated by the backend
at its edge. Client-supplied request ids are ignored. Failures use one object:

```json
{"code":"notFound","requestId":"…","messageKey":"api.notFound","retryable":false}
```

| code | HTTP | retryable | meaning |
| --- | --- | --- | --- |
| `invalidRequest` | 400 | no | malformed input, unknown keys, bad cursor |
| `unauthorized` | 401 | no | no session, or a failed device proof |
| `forbidden` | 403 | no | authenticated, but not allowed |
| `notFound` | 404 | no | absent or not visible to the caller |
| `conflict` | 409 | no | revision mismatch, spent invitation, or a different command body |
| `expired` | 410 | no | expired challenge, invitation, or cursor generation |
| `unsupported` | 501 | no | the requested runtime or adapter is not published |
| `offline` | 503 | yes | the host is not connected |
| `misconfigured` | 503 | no | a required provisioning value is missing |
| `rateLimited` | 429 | yes | retry after the advertised delay |
| `temporaryFailure` | 503 | yes | a database operation failed; details are logged, not returned |

`retryable` never authorizes repeating a mutation. Consult the receipt first.

## Catalog (read-only, anonymous)

- `GET /api/v3/catalog/items?q&kind&target&cursor&limit` — keyset page, `limit` 1–50.
  `kind` is `plugin`, `template` or `profile`; `q` is at most 100 characters.
  Unknown query keys and repeated keys are refused.
- `GET /api/v3/catalog/items/{kind}/{id}?target` — one item, or `notFound`.
- `POST /api/v3/catalog/items/resolve` — `{"items":[{"kind","id"}]}`, at most 50.
  Unknown references come back in `missing`; they do not fail the batch.

Plugins are projected from the **active registry generation**. Templates and
profiles are projected from their **published revision** (`published_revision`),
the same selection the v2 public catalog uses. Drafts and withdrawn revisions never
appear.

`dataState` is `ready` or `noActiveGeneration`. An empty registry is not an outage.

Cursors are opaque, base64url JSON bound to the query, the kind filter, the target
and the active generation. Reusing a cursor with another query returns
`invalidRequest`; a cursor from an older generation returns `expired`.

Item shape (summary): `identity` (`kind`, `id`), `presentation` (`title`, `summary`,
`publisher`, `authors`, `categories`, `tags`), `media` (`iconAssetId`, always
`null` until assets exist), `compatibility` (`targets`, `engine`, `homepage`),
`releaseRef` (`pluginRelease` with generation, version, target, sha256, size; or
`documentRevision` with revision and sha256), `publication` (status, yanked,
key and publisher state, advisory), `requirements.dependencies`.

Presentation never replaces installation metadata. Install decisions still use the
signed package and its generation.

### Presentation source

When a release passes verification, the integrity worker stores bounded display
fields read from the signed manifest: name (120 characters), summary (500),
lowercase categories (8 × 32), authors (8 × 80), engine, an HTTPS-only homepage and
dependencies (32 entries). Control characters are rejected. Migration
`20261110000001_plugin_presentation.sql` adds the columns.

Releases verified before this migration have no display fields. Their title falls
back to the plugin identifier until they are re-verified. No demonstration data is
inserted.

### Own resources

`GET /api/v3/library/items` and `GET /api/v3/library/items/{id}` list the caller's
templates and profiles in any status. They require a session (`unauthorized`
otherwise). Writes stay on the v2 library API.

## Remote control

A host opens an **outbound** WSS connection to the Cloud. Controllers never reach
the PC directly. The relay authenticates, bounds and routes commands; the host
re-evaluates every permission when it executes. The relay does not contain a second
rules engine.

### Identities and proof of possession

Devices are Ed25519 identities. Enrollment and ticket issuance require a signature
over a server-issued challenge:

1. `POST /api/v3/remote/challenges` `{purpose: "enroll"|"ticket", binding}` returns a
   single-use nonce and `bindingSha256`, valid for 60 seconds.
2. The device signs the UTF-8 message
   `tiktools.remote.v1\n<purpose>\n<nonce base64url>\n<bindingSha256>`.
   The server rebuilds that message from the stored challenge row; the client never
   supplies the signed text.
3. `POST /api/v3/remote/devices` (enrollment) or `POST /api/v3/remote/tickets`
   (ticket) verifies the signature with `verify_strict`.

A failed proof rolls back and leaves the challenge unconsumed. A spent challenge
returns `expired`.

Storing a public key does not prove identity. Only step 3 does.

### Teams, invitations, requests and grants

| Operation | Route |
| --- | --- |
| Create / list / read / update team | `POST`/`GET /api/v3/remote/hosts`, `GET`/`PATCH /api/v3/remote/hosts/{hostId}` (`PATCH` takes `expectedRevision`) |
| Enroll / list / revoke devices | `POST`/`GET /api/v3/remote/devices`, `DELETE /api/v3/remote/devices/{deviceId}` |
| Create / list / revoke invitations | `POST`/`GET /api/v3/remote/hosts/{hostId}/invitations`, `POST …/invitations/{id}/revoke` |
| Redeem an invitation | `POST /api/v3/remote/invitations/redeem` `{token, deviceId}` |
| List / decide requests | `GET /api/v3/remote/hosts/{hostId}/requests`, `POST …/requests/{id}/decision` |
| List / edit / revoke grants | `GET /api/v3/remote/hosts/{hostId}/grants`, `PATCH …/grants/{id}` (`expectedRevision`), `POST …/grants/{id}/revoke` |
| List / revoke sessions | `GET /api/v3/remote/hosts/{hostId}/sessions`, `POST …/sessions/{id}/revoke` |
| Receipt of a command | `GET /api/v3/remote/hosts/{hostId}/commands/{commandId}` (host owner or controller owner) |
| Connection ticket | `POST /api/v3/remote/tickets` |
| Relay | `GET /api/v3/remote/socket` (WebSocket upgrade) |

Rules:

- Inviting grants nothing. Redeeming approves nothing. The owner decides.
- Invitation tokens are 256-bit secrets. Only their SHA-256 is stored; they are
  shown once, expire within 15 minutes at most, and are single use.
- Owners are derived from the session. A request body cannot name another user.
  Other accounts receive `notFound` for teams they do not own.
- A decision creates a grant in `pendingHost`. It becomes `active` only when the
  host confirms the **exact revision** it persisted (`grant.confirmed` on the
  socket). Until then no ticket is issued and no command is admitted.
- Editing a grant bumps its revision, returns it to `pendingHost`, and closes every
  session opened under the previous revision.
- Revoking bumps the revision, closes sessions, invalidates unconsumed tickets and
  notifies the host. A repeated revoke is idempotent.
- A controller ticket is bound to the device, the team and the active revision of
  the grant held by the requesting account. A host ticket is bound to the team
  owner and the host device.
- An account with the cloud administrator or catalog editor role receives no
  special authority over teams.

### Preset roles

| Role | Admitted operation classes |
| --- | --- |
| `observer` | read |
| `moderator` | read, moderation |
| `automationEditor` | read, automation draft submission |
| `custom` | the explicit `allowedOperations` list in the grant policy, validated against the known operations |

Operations: `live.status`, `workflow.list`, `competition.list`, `points.read`,
`automation.list`, `command.outcome` (read); `workflow.disable`, `workflow.delete`,
`points.adjust`, `automation.toggle`, `automation.delete`, `competition.control`
(moderation); `automation.draft.submit` (draft). Anything else is refused.

The relay checks the role and the revision. The host checks permissions, resources
and limits again at execution time.

### Socket protocol

1. The first frame must be `{"type":"auth","ticket":"…"}` within 10 seconds. The
   ticket is consumed on first use, whether or not validation succeeds. A spent or
   unknown ticket yields `{"type":"error","code":"ticketInvalid"}` and a close.
2. The server replies `{"type":"ready", role, hostId, …}`.
3. Frames are JSON text, at most 128 KiB. Binary frames are refused.
   An idle socket is closed after 45 seconds. `{"type":"ping"}` answers `pong`.

Host frames:

- `grant.confirmed` `{grantId, revision}` → `ack`, or `error conflict` if the
  revision is not the current pending one.
- `result` `{commandId, status, code?, result?}` → `ack`. Allowed transitions:
  `accepted → running|completed|failed|cancelled|expired|unknown`,
  `running → completed|failed|cancelled|unknown`, `unknown → completed|failed|cancelled`.
  Terminal states never change. Results are at most 64 KiB and are forwarded to the
  controller session.

Host server frames: `grants.changed` (re-read grants over REST), `command`
`{commandId, sessionId, operation, args, expiresAt}`.

Controller frames:

- `command` `{commandId, operation, args, policyRevision, expiresAt}`. Replies:
  `command.accepted`, `command.rejected` `{code}` (`expired`, `stale`, `revoked`,
  `forbidden`, `unknownOperation`, `offline`, `busy`, `invalidArguments`, `conflict`),
  or `command.status` when a known id is replayed with the same body.
- `result` `{commandId, status, code?, result?}` from the host.
- `closed` `{reason}` when the session ends (`grantChanged`, `grantRevoked`,
  `sessionRevoked`, `deviceRevoked`, `hostDisabled`, `replaced`).

### Commands: bounds, idempotency and unknown outcomes

- `commandId`: 8–128 characters from `[A-Za-z0-9._:-]`.
- Lifetime: `expiresAt` must be in the future and at most 60 seconds ahead.
- Arguments: a JSON object of at most 16 KiB, hashed in canonical (sorted-key) form.
- A receipt is keyed by `(host, commandId)`. The same id with the same session and
  body replays the stored status. The same id with another body returns `conflict`.
  Rejected attempts also leave receipts.
- Commands are **never queued** for an offline host (`offline`).
- A command in flight when its host disconnects becomes `unknown` with
  `hostDisconnected`. It is not resent. A host that comes back does not reopen it.
- Accepted commands past their lifetime become `expired` the next time the relay
  admits a command. Running commands are not expired automatically.
- Each session has at most 8 in-flight commands; each host at most 32 controllers.
- Per-account limits per minute on write routes: challenges 60, device enrollment 20,
  team creation 10, invitations 20, redemption 30, ticket issuance 60. A limiter that
  cannot answer fails closed with `temporaryFailure`.

A dropped connection does not prove that an operation did not happen. Read the
receipt before doing anything else.

## Integrations

The first provider is a **signed inbound webhook**.

- `POST /api/v3/integrations/webhook/connect` `{label}` creates a connection and returns
  its secret **once** (64 hex characters). Only the secret sealed with AES-256-GCM is stored,
  bound to the connection id as associated data.
- Deliveries: `POST /api/v3/integrations/webhook/{connectionId}/deliveries` with
  `x-tiktools-timestamp`, `x-tiktools-delivery` and `x-tiktools-signature: sha256=<hex>`,
  where the hex is HMAC-SHA256 over `timestamp + "." + raw body`. Timestamps must be within
  five minutes of the server clock. Bodies are JSON objects of at most 64 KiB. A repeated
  delivery id answers `duplicate: true` and stores nothing new. Each connection keeps its 200
  newest events.
- `GET /api/v3/integrations/connections`, `GET …/connections/{id}/events` and
  `DELETE …/connections/{id}` (owner only). Deleting removes the sealed secret and refuses
  later deliveries; stored events stay readable.
- The server key is `INTEGRATION_SECRET_KEY`: 32 random bytes, base64. Without it the provider
  is not published and connecting answers `misconfigured`.
- Operations (`…/operations/{id}`) answer `unsupported`; no provider defines any yet.

Other providers (OAuth-based services, host-side connectors such as OBS or RCON) need their
own credentials and contracts. None is published until it is implemented and configured.

## Operations

- Apply migrations explicitly, after a backup: `20261110000001_plugin_presentation.sql`
  and `20261110000002_remote_control.sql`. Migrations are not reversible here; restore
  the backup to roll back.
- **The relay runs on several replicas.** Each replica is a relay node (`RELAY_NODE_ID`, or a
  random id per process). A connection is owned by one node through a lease (30 seconds,
  renewed every 10). The lease carries a fencing token that grows whenever ownership moves; a
  node that cannot renew its lease closes the connection. Frames for a connection owned by
  another node are queued in PostgreSQL (`cloud_relay_frames`, 128 KiB each) and drained by the
  owner every 200 ms. Migration `20261110000004_relay_coordination.sql` adds the tables.
- Trusted origins are the existing `AuthOptions.trusted_origins`. A WebSocket upgrade
  that presents an `Origin` outside that list is refused with `forbidden`. Requests
  without an `Origin` (native clients) are accepted; the ticket is what authenticates.
- Accepted commands whose lifetime has ended are marked `expired` by a background sweeper
  every 5 seconds, sharing the relay hub. Running commands stay in flight.

## Media, overlays and packages (section 9.1)

- **Assets** `POST /api/v3/assets` accepts raw PNG, JPEG or WebP bytes up to 512 KiB.
  The format is read from the signature bytes, dimensions from the header
  (4096 pixels maximum per side), and pixels are never decoded. SVG is refused.
  Identical bytes return the existing id. Quotas per account: 200 assets and 32 MiB.
  `GET /api/v3/assets/{id}` serves the owner only, with the verified content type
  and `X-Content-Type-Options: nosniff`.
- **Overlays** `POST /api/v3/overlays`, `GET /api/v3/overlays/{id}`,
  `POST /api/v3/overlays/{id}/revisions` (`expectedRevision`). Schema version 1:
  canvas 320–3840 × 180–2160; up to 64 elements of type `text`, `avatar` or `art`;
  geometry must fit the canvas; text comes from a static string or an allow-listed
  event field; art references an asset owned by the same account. Unknown keys are
  refused. Kinds: follow, gift, chat, share, subscribe, likes, ranking. Overlays stay
  private and are never published through the v2 review.
- **Packages** `POST /api/v3/packages`, `GET /api/v3/packages/{id}`,
  `GET /api/v3/packages/{id}/preflight`. A package pins each reference: plugins by
  version (checked against the active generation), templates and profiles and
  overlays by revision. Creation refuses missing or drifted pins. Preflight reports
  each item's current status (`ready`, `missing`, `notInstallable`,
  `revisionChanged`, `noActiveGeneration`), what blocks application, and
  `applyMode: clientJournal`. Plugin permissions are shown by the host's consent
  step because the backend does not store them (`reviewRequired`). Imported
  automations stay disabled (`disabledUntilExplicit`).

Applying a package is performed by the client, which uses the existing install and
import flows. The backend never applies a package.

## Not implemented (explicit)

- **Integration providers beyond the signed webhook**: they require their own credentials and
  contracts.
- **Host-side client**: the WSS client, grant persistence and confirmation are implemented in
  TikTools-app, not in this repository.
- **Overlay and package rendering in the app** and the **apply journal** are client work.
