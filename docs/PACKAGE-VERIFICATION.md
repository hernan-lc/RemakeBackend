# Package verification boundary (experimental)

`cloud-verifier` uses the TikTools package and manifest crates pinned to PR #43 commit `983a375c5b702681a791061ca863cea9c542528d`. The one-shot Cloud integrity worker calls this library for submitted, version-pinned uploads; the worker additionally streams its verified copy to ClamAV, and moderation decisions can be recorded; an isolated reviewer inspection environment and publication remain unimplemented.

The caller supplies a server-controlled local file, expected namespace, plugin ID, version, target and SHA-256, plus a publisher key obtained from an independently authorized source. The verifier copies the file into a private temporary directory, checks the digest, limits archive size, entry count, declared expanded size and per-entry expansion ratio, validates manifest identity and the target used by the upstream registry writer, checks the publisher signature and scope using the upstream trust store, and invokes upstream extraction and checksum validation. It returns a handle to the private copy; the original path must not be published. Recheck the copied artifact's digest and key authorization when persisting and again when publishing.

This does **not** establish that a key belongs to a publisher, approve a namespace, scan malware, enforce a complete archive resource sandbox, detect every malformed or hostile archive, protect against every local filesystem race, provide idempotency, or make a release publishable. The caller must not accept arbitrary local paths from clients. Untrusted archives require isolated workers with CPU, memory, disk, concurrency and execution-time limits, plus a separately designed malware/security policy and moderation. Approved keys can be revoked between verification and publication, so publication must check current authorization again. The extracted temporary tree is deleted when the result is dropped; retention and crash cleanup still need operational design.

Tests generate signed packages with the upstream library and check a valid copy, digest and identity mismatches, forged and revoked/expired keys, checksum tampering, path traversal and high expansion. The `verify_fixture` example also checks the disposable CLI-generated registry fixture; it reads its test key from the fixture itself and must never be used as a production trust source. CI runs these tests and the fixture example. These tests alone are not evidence of real object-storage, antivirus configuration or publication integration. The worker has a separate simulated-storage integration test.
